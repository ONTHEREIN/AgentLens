## 1. 三十秒版：我们到底在做什么

**AgentLens 是一个给 AI 智能体做「分层归因体检」的测试平台。**

普通测试告诉你 `FAIL`。AgentLens 告诉你 `FAIL 在 L2 工具选型`，并给出复现命令。

具体来说，它做三件事：

1. 把智能体的一次执行录成**分 span 的 trace**（`plan` / `tool_call` / `observation` / `retrieve` / `generate` / `guardrail`）
2. 对每个 span 下**独立的断言**，判定这一步对不对
3. 把失败的用例**归因到六层之一**（L0 环境 ~ L5 知识，L6 护栏误伤单列），最后出一张「维度 × 根因」缺陷热力图

**被测对象**是我们自己给软帮手 OneGZUS（真实的校园服务产品，已上线）新加的 agent 功能：6 个只读工具，查课表、成绩、考勤、考试安排、宿舍水电余额，检索校园通知。agent 没有任何写操作。

**核心主张一句话：测链路，不是测答案。**

## 2. 为什么是这个东西（赛题定位）

赛道全称：**AI赋能·智能测试创新挑战赛**（2026 第九届传智杯，技术应用赛/团队赛）。

官方给了**两条参赛路径，任选其一**：

| 路径 | 做什么 | 我们 |
|---|---|---|
| **路径一** | 先基于 Dify / Coze / LangChain 搭一个智能体应用，再对它做全方位测试 | ❌ 不走 |
| **路径二** | 开发专门针对 AI 智能体的**测试工具或平台** | ✅ **主战场** |

为什么不走路径一：它的第一条硬性要求是「基于 Dify / Coze / LangChain 搭建」，而我们的被测 agent 是自研 Python（为了让每一步都能埋点）。**硬走路径一，评委一句"你这智能体不是用框架搭的"就把 30% 那项打成中档。**

而路径二举的四个官方例子里，第三个是：

> 智能体行为可视化与审计平台：记录并可视化智能体的"思考-行动"链路，辅助缺陷定位

**这就是官方替我们写好的产品描述。**

### 但路径一的东西我们全要

路径一要交五份东西：应用介绍、测试方案文档、测试用例集、测试执行记录、缺陷分析报告。
路径二要交三份：可运行的原型、技术方案说明、**实际应用效果验证**。

**这两批东西是同一批东西。** 做一份工作，同时拿三个分：

- 路径二的 **创新性 20%**
- 路径一的 **智能体理解与测试深度 30%**（七维度全覆盖）
- 路径一的 **完整性 10%**（端到端执行并产出可验证结论）

这也解释了**为什么必须给软帮手加 agent**：路径二明写要「实际应用效果验证」，没有真实被测对象，这一项就是空的。

### 评分标准（官方表格原文）

| 权重 | 维度 |
|---|---|
| 30% | 智能体理解与测试深度（是否覆盖多种智能体类型与失败模式） |
| 25% | AI 能力应用水平（是否充分利用 AI 技术辅助测试） |
| 20% | 创新性（测试方法或思路是否有别于传统软件测试） |
| 10% | 完整性（是否覆盖完整测试流程） |
| 10% | 实用性与商业价值 |
| 5% | 社会价值 |

**60% 押在前两项。** 而这两项恰好是最容易做浅的——所以下面第三节最重要。

## 3. 三个最容易搞混的概念

新人第一天最常问："七维度、六类 span、六层归因，到底啥关系？"

**答案是：它们几乎不是一一对应的。** 这张表请背下来。

| 概念 | 回答什么问题 | 数量 | 性质 |
|---|---|---|---|
| **七维度** | 我们在**测什么** | 7 | 官方定义的横轴，一字不能改 |
| **六类 span** | 我们从 trace 里**能断言什么** | 6 | 我们自己的技术抓手 |
| **六层归因 L0–L6** | 失败**归到哪去** | 7 | 我们的纵轴，独占价值所在 |

### 七维度（官方原文，横轴）

1. 功能准确性测试
2. 工具调用测试
3. RAG 检索质量测试
4. 多轮对话测试
5. 对抗性与安全测试
6. 边界与异常测试
7. 性能测试

### 六类 span（技术抓手）

| span | 能断言什么 | 对应归因层 |
|---|---|---|
| `plan` | 意图对不对、该不该分步 | L1 |
| `tool_call` | 选对工具了吗、参数填对了吗 | L2 / L3 |
| `observation` | 工具本身返回的东西健不健康 | L0 / L5 |
| `retrieve` | 召回的内容相关吗、够吗 | L5 |
| `generate` | 把上游结果解读对了吗 | L4 |
| `guardrail` | 该拒的拒了吗、误拒了吗 | L6 |

### 六层归因（纵轴）

```
L0  环境/超时       上游超时、网络失败、凭证过期
L1  意图与规划      理解错用户要什么，或多步任务只做了一步
L2  工具选型        选错工具，或该调工具没调
L3  参数填充        工具对了，参数错了（学期、课程名、日期）
L4  结果解读        数据拿对了，结论说错了
L5  知识与检索      召回不相关，或没有对应知识还硬答
L6  护栏误伤        该拒的没拒 / 不该拒的拒了 ← 单列，不和上面混
```

**为什么 L6 要单列**：该拒和误拒是方向相反的两个问题，混在一起统计会互相抵消，掩盖真实缺陷。

### 三个概念的交叉关系（重点）

- `功能准确性` 和 `边界与异常` 这两维**没有专属 span**，要靠 span 组合判
- `多轮对话` 靠 `conversation_id` + `turn` 串起来的多条 trace 判
- `性能` 靠 span 上挂的 `latency_ms` 判，不需要新 span 类型
- 一个失败样本**可以拆出多个根因**（例：「图书馆几点关门」既选了错工具 L2，又对低相关度内容给了确定答案 L5）

## 4. 五个已经定死、不要再讨论的决策

如果想推翻其中任何一条，先说服我，别自己改。

### ① 走路径二，不搭 Dify 应用

见第 2 节。**路径一的产物我们照做，但主身份是"测试工具"。**

### ② 不用 Dify 搭被测对象

官方技术栈推荐 Dify。我们评估后不用，理由是硬的：

Dify 给你**最终答案**、**几行运行日志**、**token 数**。它不给你：
- span 层级的**父子关系**（哪个工具调用属于哪一步规划）
- **分段延迟**（哪一步慢）
- 工具返回的**原始结构**（只知道"调用了"，不知道返回了什么）

而五层归因的物理基础就是这三样。没有它们，归因只能靠 LLM 猜——**那就不是测试，是算命。**

> 待办（截至 11/14 仍未做）：需要一个 30 分钟的 Dify 试搭 + 三张截图，把上面这段从「我们的说法」变成「我们看到的事实」。放进作品介绍文档第四节。
> 在那之前，材料里这段只能当论证写，不能写成实测结论。

### ③ trace 必须是**录下来的**，不是造出来的

现在 `agentlens/adapters/campus_copilot.py` 是桩：`if-else` 按固定顺序拼出 span。
**这个桩只用来验证测试框架本身自洽，最终版的 trace 必须来自真实 agent 的真实运行。**

做法：adapter 加 `record` / `replay` 双模式。录一次真 LLM 运行，之后离线回放。
注意：官方说的"缓存回放"≠"伪造 trace"。回放的是真的录下来的东西。

### ④ 判定走**双轨**，不是纯规则

| 轨 | 判什么 | 特性 |
|---|---|---|
| 确定性 span 断言 | 工具选型、参数合法性、观测结构、检索相关性、护栏方向 | 可复现、可解释、零成本、可审计 |
| LLM 语义裁判 | 答案忠实度、多轮连贯性、护栏是否**过度**拒答、回答有用性 | 需要模型、有方差 |

**这不是妥协，是必须。** 官方 25% 那项明写「AI 自动判定测试结果」，如果我们宣称"全部用确定性规则、一条 LLM 都不用"，等于在 25% 的项上主动弃分。

同时要交一件事把两轨缝起来：**用 Cohen's Kappa 证明 LLM 裁判和人工标注一致**（目标 ≥0.75）。这样"用了 AI"和"AI 可信"同时成立。

### ⑤ 写操作 agent 不代用户提交

请假是真实业务，有两段式（`leave_preview` → `leave_fill`）且强制至少一张附件。
当前的 agent 干脆没有写工具；以后要加，也只做到「生成预览 + 追问缺件 + 出表单」，**最后一下由用户点**。

## 6. 分工与写作边界

原计划三人分工，实际由 rein 一人维护全部代码与材料；AI 助手按 rein 的指示改代码，规则相同。

### 三条不可越的线

1. **`schema.py` 改动需 rein 拍板。** 它是产品地基，所有文件依赖它。
2. **分支**：AgentLens 在 `feat/agent` 上开发，阶段完成后快进合入 `main`。软帮手只推 `feat/agent`，
   **永远不推、不合 master**：master 一推就触发生产部署。改被测对象（软帮手的 agent）也要先经 rein 同意。
3. **提交要细粒度。** 官方原文：「保留完整、细粒度的 Git 提交历史（禁止一次性提交即包含全部功能），每次提交应对应一次与 AI 的核心对话或一个功能模块的落地」。**一次提交 = 一件事。**

## 8. 术语表

| 词 | 意思 |
|---|---|
| **trace** | 一次执行的全过程记录，由多个 span 组成 |
| **span** | trace 里的一步，带 kind / 输入 / 输出 / 耗时 |
| **adapter** | 被测对象的适配器，把不同 agent 的输出统一成 trace |
| **case** | 一条测试用例（YAML），含输入、期望、维度、来源 |
| **oracle** | 判定"对错"的标准。智能体测试的难点就在这——输出没有唯一正确答案 |
| **归因** | 把一次失败定位到 L0–L6 中的某一层 |
| **replay** | 回放录制好的 trace，不重新调用模型，保证可复现 |
| **FaultySource** | 故障注入器，包在真实数据源外面，按计划制造超时/空数据/schema 错 |
| **golden / mutated / injected** | 用例的三种来源：手写种子 / 变异生成 / 故障注入 |
| **Kappa** | Cohen's Kappa，衡量两个标注者（比如 LLM 裁判和人工）一致程度的指标 |

## 9. 十条不要做

1. **不要改 `schema.py`。**
2. **不要为了让用例通过去改被测对象的行为**——那是在作弊，评委一眼看穿。
3. **不要把失败的用例改成期望通过**。失败是资产，我们的交付物就是缺陷清单。
4. **不要用 mock 替代真实数据**，除非是 `FaultySource` 有意的故障注入。
5. **不要引入运行时需要联网的依赖**。演示不能押在网络和 API 额度上。
6. **不要在用例里写"期望 LLM 回答得好"**这种无法断言的东西。
7. **不要一次性提交几千行**。官方查 Git 历史，一次性提交 = 原创性存疑。
8. **不要自造第八个维度**。七维度是官方原文（"包括但不限于"，但我们不冒险加）。
9. **不要因为门禁失败就删用例或跳过检查**。
10. **不要向学校真实系统发写请求**（请假、报修）。只读可以，写只用 `FixtureSource`。

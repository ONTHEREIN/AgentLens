# 故障注入校准记录（2026-11-07）

目的：用「根因已知」的失败样本给 AgentLens 自己打分——裁判能不能发现（检出率），
归因能不能归对层（归因准确率）。真实缺陷要靠人复核才知道根因，样本又少，量不出这两个数。

## 两条注入通道

| 通道 | 改什么 | 样本 | 已知根因 | 是否调用模型 |
|---|---|---|---|---|
| 录制变异（`agentlens/inject.py`） | 对 30 条已通过的真实录制，定点改写一处 LLM 回复，回放时工具照常执行 | 159 条（`cases/calibration/`） | L0–L4，由算子决定 | 否，纯回放 |
| 数据面故障（软帮手 `FaultySource`） | 让指定数据源报错，或静默篡改返回字段，再由真实模型作答 | 11 条（`cases/faults/`） | 报错类 L4（若编造）、篡改类 L5 | 录制一次，之后回放 |

7 个变异算子：`truncate`(L0) `drop_plan` `plan_drift`(L1) `swap_tool`(L2) `wrong_arg` `bad_arg`(L3) `answer_tamper`(L4)。

复现：

```bash
python -m agentlens inject cases/onegzus/                                  # 重新生成变异用例
python -m agentlens run cases/calibration/ --adapter onegzus               # 变异集
python -m agentlens run cases/faults/ --adapter onegzus --llm-judge        # 数据面故障（命中裁判缓存，不联网）
```

## 结果与修正（按时间顺序，保留每一版的数字）

| 版本 | 变异集检出率 | 变异集归因准确率 | 篡改用例归 L5 | 变化 |
|---|---|---|---|---|
| v0 | 102/160 = 63.7%（95% CI 56.1–70.8） | 102/102 | 0/3（全部误归 L4） | — |
| v1 | 157/160 = 98.1% | 157/157 | — | 规则轨补 `plan`、`tool_schema` 两条断言（`29d0d34`） |
| v1′ | 159/159 = 100%（CI 97.6–100） | 159/159 | — | 剔除 1 条等价变异（`ecfed85`），见下 |
| v2 | 159/159 | 159/159 | 3/3（双轨）/ 0/3（仅规则轨） | 归因区分「读错」与「数据错」（本次最后一个提交） |

暴露出的三处问题：

1. **规则轨没有规划断言**：删掉计划、计划与执行脱节，55 条变异中有 51 条判为通过。
   补上的 `plan` 断言要求：有工具调用就必须有计划，且计划里的工具集合与实际调用一致。
2. **参数非法后没有重试也不算失败**：补上 `tool_schema` 断言，要求参数非法之后必须用合法参数重试成功。
   另有 3 条变异本身就是等价的（agent 后面用合法参数重试了，或者这个回答本来就不需要调用工具），
   这一类从生成阶段就排除，不计入检出率。
3. **归因分不清「agent 读错」和「数据本身错」**：静默篡改的数据，agent 照实转述，归因却判成 L4。
   先试了「期望内容在观测里找不到就归 L5」，结果在变异集上误伤 5 条：均分 88.6、绩点 3.72、
   总学分 14 这类是 agent 自己推算出来的值，本来就不会出现在原始数据里。最终规则是：
   **只有 LLM 裁判给出正面证据、确认答案忠实于观测时，才归 L5。** 只跑规则轨时保守归 L4。
   这说明 L4 和 L5 的区分单靠规则做不到，需要双轨判定。

## 必须如实说明的局限

- **变异集上的 100% 有循环论证的成分**：7 个算子是对着归因决策树的 7 个分支设计的。
  这个数字只能证明决策顺序没有互相抢判，不能说明归因器面对真实缺陷时有多准。
  真实缺陷上的准确率，要看数据面故障用例（真实模型作答）和人工复核的 κ。
- 篡改类只有 3 条，L5 的 3/3 对应的 95% CI 是 43.8–100，样本还远远不够。
- L6（护栏）没有注入：护栏是规则，不经过 LLM 回复，录制变异改不到它。

## 被测对象的表现（数据面故障）

- 超时、登录失效、接口未实现、字段异常这 8 条，agent 全部如实告知用户，没有编造任何数据。
  规则轨和 LLM 裁判的结论一致。
- **D-002（低）**：agent 把 `not_implemented`、`auth_expired`、`schema_mismatch`、`upstream_timeout` 这类内部错误码
  直接写进了给用户的回答（8 条中有 6 条），属于用户体验问题。
- 静默篡改的 3 条，agent 都忠实转述了错误的数据。这是预期行为：根因在数据源，不在 agent。

## 补充：双轨复跑变异集（`--llm-judge`）

| | 规则轨 | 规则轨 + LLM 裁判 |
|---|---|---|
| 检出率 | 159/159 | 159/159 |
| 归因准确率 | 159/159 | 158/159（95% CI 96.5–99.9） |

- **LLM 裁判单独看并不灵敏**：13 条被篡改的答案里，它只判出 8 条不忠实（62%）。
  另外 5 条是靠规则轨的关键词断言抓到的。所以「能用规则判的不交给 LLM」这一原则有了数据支撑。
- 归错的那 1 条是 `mt_pronoun_course_001__answer_tamper`：变异把「请假」替换成了「……」，属于省略，
  不是说错，LLM 裁判判为忠实（5/5），于是触发了 L5 规则。这是 L5 规则依赖 LLM 正面证据带来的代价，
  如实记录，不为它再加特判。

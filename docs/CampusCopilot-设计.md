# CampusCopilot 设计 · 参考被测对象

| 项 | 内容 |
|---|---|
| 版本 | v1 设计稿（2026-10-25） |
| 定位 | AgentLens 的**首个被测对象**，不是交付主体 |
| 前置状态 | M0 已跑通，v0 是确定性规则实现（`rule-based@v0`，单步、3 处刻意缺陷） |
| 本文目的 | 把"靶子"从**夹具**升级成**真实被测对象**，让缺陷由架构与模型自然产生，而不是我埋 |

---

## 0. 一句话

> **把「我要办某事」翻译成「调哪几个接口 + 引用哪条规章 + 下一步怎么做」。**

边界（v1 明确不做）：

| 不做 | 原因 |
|---|---|
| 通用闲聊 | 闲聊直接引导回办事范围，否则测出来的都是闲聊质量，浪费用例预算 |
| 真实学校系统 | 一律录制回放 / 构造数据（合规红线） |
| 多步写事务 | 报修是唯一写操作，且幂等可撤销；跨系统事务会把状态一致性引入测试范围，范围爆炸 |
| 多模态输入 | trace schema 复杂度会翻倍（PRD 已列为非目标） |
| 产品化 UI | 只要"能被测"的最小形态：一个对话入口 + 结果卡 |

---

## 1. 为什么现在才设计它（顺序不是随便定的）

有人说应该先做好 Agent 再搭测试平台。反了。

**尺子的刻度，决定了被测物的形状。**
AgentLens 的六类 span 不是事后想加的日志字段，它直接规定了 Agent 必须把哪些阶段拆成独立模块：

- 要能断言"意图对不对"，plan 就必须是**独立可读**的产物，不能藏在 prompt 里
- 要能断言"工具选得对不对"，工具选型就必须发生在**调用之前**，而不是边调边想
- 要能断言"召回对不对"，retrieval 就必须与 generate **分离**，不能一个模型一把梭

所以正确的顺序是：先定尺子（M0 已做），再造被测物（现在）。这也正是产品要讲的第二个价值——
**AgentLens 反过来约束了 Agent 的架构，让它天生可观测。** 这句话写进材料时，比任何性能数字都值钱。

---

## 2. 六模块架构：每个模块 = 一个可断言点 = 一种失败模式

模块划分不是按功能切的，是按**"怎么坏"**切的。这是整份设计里唯一不可妥协的地方。

| # | 模块 | 职责 | 产出 span | 它能怎么坏 |
|---|---|---|---|---|
| 1 | 前置护栏 Guardrail(pre) | 越权 / 敏感 / 注入的输入过滤 | `guardrail(stage=pre)` | 越权放行、误拒 |
| 2 | 规划器 Planner | 意图分类 + 步骤规划（1–3 步） | `plan` | 漏步骤、意图跑偏、多意图只抓一个 |
| 3 | 工具执行器 Executor | 参数填充 + schema 校验 + 调用 + 观测捕获 | `tool_call` + `observation` | 选错工具、编造参数、异常没兜住 |
| 4 | 检索器 Retriever | 规章召回 + 打分 | `retrieve` | 零召回、top_k 截断漏条款 |
| 5 | 生成器 Generator | 答案合成 + 引用标注 | `generate` | 过度概括、引用张冠李戴、答非所问 |
| 6 | 后置护栏 Guardrail(post) | 答案审查（泄漏他人数据 / 编造条款） | `guardrail(stage=post)` | 泄漏、放行编造内容 |

**为什么必须双层护栏**：v0 只有前置，所以"护栏误伤"和"护栏漏放"只能测出前者。
真实的护栏一定是"入口拦一次、出口再审一次"，两层的失败模式完全不同，混在一起就测不准。

## 3. Planner：为什么必须是两阶段、必须能多步

```
Stage A 意图分类
  single_tool | multi_tool | chitchat | refuse
Stage B 步骤规划（仅 multi_tool 进入）
  产出 1–3 步的执行序列，每步 = (tool, 目的, 参数意图)
```

**单步 Agent 的 L1 层永远测不出来**——因为它没有"规划"这个可错的环节，一切都能事后解释成"它就是那么想的"。
所以多步能力不是为了功能完整，是为了让 L1 这一层**存在**。

典型多步场景（也是最好的 L1 用例来源）：
- "第 8 周有没有调课？要办什么手续" → `get_timetable` + `search_regulations`
- "我成绩够不够毕业？不够的话怎么补" → `get_grades` + `search_regulations`
- "校园卡丢了怎么办" → `search_regulations` +（可选）`submit_repair`

单步实现遇到这些必然只做一半，且**答案看上去还挺像样**——这才是最危险的失败，也是 L1 归因的用武之地。

## 4. 工具设计：描述本身就是缺陷源

5 个工具（沿用 M0）：

| 工具 | 参数 | 说明 |
|---|---|---|
| `get_timetable` | `week:int, term:str` | 课表 |
| `get_grades` | `term:str` | 成绩 |
| `get_card_balance` | — | 校园卡余额与消费 |
| `search_regulations` | `query:str, top_k:int` | 校历规章 RAG |
| `submit_repair` | `location:str, issue:str` | 提交报修 |

**关键取舍：工具描述要写得像真人写的，不要写得像 API 文档。**

真实项目里的工具描述往往有重叠、有模糊边界（"获取课程相关信息"——课程是课表还是成绩？）。
如果我把它写得滴水不漏，L2 这一类失败就永远不会自然发生，只能靠我故意埋。

所以 v1 的描述原则：
1. 每个描述**不超过两句话**，允许存在语义重叠区（课表 / 成绩 / 学分之间）
2. **不写"什么时候不要用我"**（真实的工具描述极少写反面条件）
3. 参数描述只写类型与业务含义，不写取值样例

这三条会让 L2/L3 的失败率显著上升——但这是**真实世界的失败率**，不是我编的。

## 5. 记忆：会话级、短、会过期

```python
session = {
  "last_term": "2025-2026-2",
  "last_week": 8,
  "last_courses": ["数据结构", "计算机组成原理"],
  "pending_slot": {"tool": "submit_repair", "missing": ["location"]},
  "turn": 3,
}
```

- **只为指代消解服务**："那门课""上周那个""就它" 能否接回实体，直接决定多轮用例能否成立
- **有效期 3 轮**：超过就丢弃。这一条是刻意的——它会让"跨 4 轮的指代"自然失败，制造真实的 L1 样本
- **槽位补全**：`pending_slot` 用于"报修缺地点 → 追问 → 用户补一句 → 继续"。这是多轮里最容易被做坏的一环

不做长期记忆 / 用户画像：那是产品化功能，与"能不能测"无关。

## 6. 双层护栏

| 层 | 规则类型 | 拦什么 | 失败方向 |
|---|---|---|---|
| pre | 越权（查他人）、注入（忽略上述指令）、敏感 | 学生信息越权、提示词注入 | 越权放行 / 误拒（L6） |
| post | 泄漏（他人学号成绩）、编造（条款编号不存在于召回集） | 出口内容审查 | 泄漏 / 误拒 |

post 层有个额外价值：**它能独立验证 L4/L5**。如果 generate 编了一个 `reg_999` 这种不存在的 chunk_id，
post 护栏可以拦下——拦下了是安全，没拦下就是一条可定位的缺陷（证据指向 `generate.citations`）。

## 7. LLM、可复现、成本

| 项 | 决策 | 理由 |
|---|---|---|
| 模型 | DeepSeek 系，`temperature=0` | 中文与 function calling 够用；版本号在 M1 第 1 天实测后**锁死写进 trace** |
| 缓存 | 内容寻址 `LLMCache`：key = sha256(model + prompt + params) | G4 复现的地基。同一批用例两次跑必须逐 token 一致 |
| 模式 | `live` / `replay` / `strict-replay` | `strict-replay` 遇缓存未命中直接报错 —— **演示现场绝不偷偷走网络** |
| 成本 | 被测 Agent 用主模型，裁判用小模型；规则能判的不调模型 | 全量 300 条一轮 < ¥20（PRD 目标） |

缓存不是优化，是**正确性要求**。没有它，"复跑差异 ≤1pp" 这条指标毫无意义。

## 8. 缺陷的诚实来源（这份设计最要命的一节）

评委会问：*这些缺陷该不会是你自己埋的吧？*

答案必须站得住。所以 v1 的缺陷分三类，**只有 A 和 B 算产品成果**：

| 类 | 来源 | 举例 | 算不算成果 |
|---|---|---|---|
| **A 结构性** | 架构决定的必然 | 单步规划在多意图下漏步骤；工具描述重叠导致误选；top_k 截断漏条款 | ✅ **算** |
| **B 模型性** | LLM 自然产生 | 参数编造（`week` 猜成当前周）、答案过度概括、引用张冠李戴、跨 4 轮遗忘 | ✅ **算** |
| **C 注入性** | 我故意的（v0 那 3 处） | 关键词首命中、敏感词护栏 | ❌ **只做回归夹具** |

**v0 的 `campus_rule` 保留，但降级为"确定性夹具"**——它的用途是：CI 里验证归因引擎本身没坏（已知输入 → 已知层），
而不是充当"发现缺陷"的证据。两者混谈，整个作品的可信度会塌。

### 预期缺陷分布（假设，非结论）

首轮体检目标 ≥15 个可定位缺陷，预期分布：

| 层 | 预期个数 | 主要来源 |
|---|---|---|
| L1 意图与规划 | 3 | A：多意图漏步骤、记忆过期 |
| L2 工具选型 | 4 | A：描述重叠 |
| L3 参数填充 | 3 | B：编造 week/term |
| L4 结果解读 | 3 | B：过度概括、把"有课"答成"要上课" |
| L5 知识与检索 | 2 | A：top_k=3 截断 |
| L6 护栏误伤 | 2 | A：前置规则过宽 |

⚠️ 这张表是**先验假设**，M2 出数后必须回填真实分布并保留偏差说明。不要拿它当结论写进材料。

## 9. 双轨 adapter

```
adapters/
├── campus/
│   ├── guardrail.py    # pre / post 两层
│   ├── planner.py      # Stage A/B
│   ├── executor.py     # 参数填充 + schema 校验 + 观测捕获
│   ├── retriever.py    # RAG
│   ├── generator.py    # 合成 + 引用
│   ├── memory.py       # 会话记忆
│   └── llm.py          # 客户端 + LLMCache + 三模式
├── campus_copilot.py   # 组装：campus_llm（真靶子）
└── campus_rule.py      # v0 冻结版：确定性夹具，不许改
```

- `campus_llm` = 被测对象，缺陷由 A/B 类产生
- `campus_rule` = 回归夹具，已知输入 → 已知层，用于验证归因引擎自身
- **Adapter 契约不变**（`invoke(case) -> AgentOutput`），M0 的抽象在这里变现

## 10. schema 增量（v0.2，两处加法，均向后兼容）

```python
class GuardrailSpan(BaseSpan):
    stage: Literal["pre", "post"] = "pre"      # 新增，默认 pre 兼容 v0

class PlanSpan(BaseSpan):
    steps: list[str]                            # 保持纯工具名，供序列比较
    arg_hints: dict[str, dict] = {}             # 新增：工具名 -> 参数意图
```

- `stage`：区分前置/后置，L6 统计时按层分开看
- `arg_hints`：让 L1 能判断"计划里想传什么"与"实际传了什么"，不必把 `steps` 改成结构化对象
- 两处都有默认值，v0 的 trace 仍能读

## 11. 落地顺序（塞进 M1 五天）

| 天 | 做什么 | 出口 |
|---|---|---|
| D1 | 拆模块骨架 + `llm.py`（客户端/Cache/三模式）+ Planner Stage A | 一条单工具用例端到端走通，trace 六类 span 齐全 |
| D2 | Planner Stage B（多步）+ 记忆 + 双层护栏 | 多轮用例 ≥3 条跑通，指代能接回 |
| D3 | Retriever + Generator 引用标注 + post 护栏的条款存在性校验 | RAG 用例能给出 citations 且可核 |
| D4 | 用例扩到 50 条（7 维度）+ `campus_rule` / `campus_llm` 对照跑 | 两轨同一批用例出结论，差异可解释 |
| D5 | 缺陷清单初稿 + 归因抽查 20 条 | ≥10 个可定位缺陷，人工认同率 ≥80% |

**风险**：D1 的 LLM 接入最容易吃掉两天（key、限流、function calling 格式）。
缓解：先用 `strict-replay` + 手工种子缓存跑通链路，再接真实调用。

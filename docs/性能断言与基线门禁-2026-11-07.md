# 性能断言与基线门禁（2026-11-07）

## 一、性能断言（performance 维度）

### 写法

用例里加 `expect.budget`，写了的上限都要满足：

```yaml
expect:
  budget:
    latency_ms: 8000     # 端到端耗时
    tokens: 8000         # prompt + completion
    tool_calls: 2        # 工具调用次数
```

规则轨的 `budget` 断言超出任意一项即失败，证据指向耗时最长的 span。

**回放可复现**：软帮手的 tracer 是虚拟时钟，模型耗时取录制值，数据源耗时由 fixture 实测（亚毫秒级）。
同一份录制回放三遍，耗时、token、判定完全一致（误差 ≤ 0.1ms）。所以性能断言不依赖网络，也能进门禁。

### 预算怎么定

预算按产品 SLO 定，**不按录制结果反推**。反推出来的预算只会让用例永远通过：

| 类型 | 耗时 | token | 工具调用 |
|---|---|---|---|
| 单数据源查询 | 8 s | 8000 | 2 次（1 次必要 + 1 次重试余量） |
| 多数据源查询 | 15 s | 15000 | 4 次 |
| 不需要查数据的问答 | 5 s | 4000 | 0 次 |

### 归因

只有性能预算不过、答案没问题时，单独归因。这一步插在 L5 之前，否则带检索的用例会被误归到知识源：

- 工具调用超次数 → **L1** 规划冗余
- 耗时超预算 → **L0** 环境，理由里拆出数据源和模型各占多少毫秒
- 只有 token 超预算 → **L1**，并标注需人工复核

答案本身也有问题时，按原决策顺序先归 L4。

### 结果

5 条 performance 用例（`cases/onegzus/perf_*`）：4 条通过，1 条失败。

| 用例 | 耗时 | token | 工具调用 | 结论 |
|---|---|---|---|---|
| `perf_schedule_today_001` | 2980ms | 4715 | 1 | 通过 |
| `perf_card_balance_001` | 3886ms | 4745 | 1 | 通过 |
| `perf_multi_source_001` | 4721ms | 5654 | 3 | 通过 |
| `perf_capability_001` | 3125ms | 2943 | 0 | 通过 |
| `perf_notice_search_001` | 4830ms | 7179 | **9** | **失败，L1** |

**D-007（中，L1）通知检索扇出**：问「最近学校有什么通知」，agent 计划里只写了一步 `search_notices`，
执行时却依次用「通知、教务、考试、选课、活动、讲座、奖学金、宿舍、图书馆」9 个关键词各搜了一次。
演示数据源是本地 fixture，所以总耗时不长；换成真实接口，就是 9 次网络请求。

根因可能在工具设计：`search_notices` 必须传关键词，没有「列出最近通知」的用法，agent 只能靠猜关键词来覆盖。
那样应归 L2（工具与需求不匹配）。归因器按「超调用次数」归了 L1，**这条需要人工复核**。

### 数据面变慢（故障注入）

软帮手 `FaultySource` 新增 `slow` 故障：数据照常返回，只叠加耗时（虚拟时钟，不真的 sleep）。

| 用例 | 注入 | 端到端 | 规则轨 | 双轨 |
|---|---|---|---|---|
| `fault_grades_slow_001` | 成绩源 +9000ms | 12594ms | L0 ✓ | **L4 ✗** |
| `fault_notices_slow_001` | 通知源 +9000ms | 13018ms | L0 ✓ | L0 ✓ |

归因理由示例：「端到端 12594ms 超出预算 8000ms，主要耗在数据源 9000ms（最慢 s3）；数据源合计 9000ms / 模型合计 3594ms」。

带检索的那条没有误归 L5，说明预算分支插在 L5 之前是对的。

双轨下 `fault_grades_slow_001` 归了 L4。这不是归因写错了，是同一条 trace 有两个根因：
注入的延迟（L0），加上 agent 在回答里又把加权绩点算成了 3.74（正确值 3.72，D-001 复现）。
按决策顺序，答案问题优先于性能问题。这里只返回一个层是归因器的设计取舍，如实记录，不加特判。
这也说明真实模型作答的故障用例不是循环论证：注入的根因会和被测对象自己的缺陷撞在一起。

## 二、基线门禁与修复前后对比

```bash
python -m agentlens compare <基线 run_id> <本次 run_id>      # 拦截时退出码 1
python -m agentlens run cases/onegzus/ --adapter onegzus --baseline <run_id>
    [--max-regressions 0] [--latency-tolerance 0.2]
```

审计台「运行对比」页（勾选两次运行）显示同一份结论，A 为基线、B 为本次。CLI 和页面都调用 `audit.gate()`。

### 修复状态

按用例对齐，两边各取首条 trace，每条用例归入以下一种状态：

| 状态 | 含义 |
|---|---|
| 新增失败 | 基线通过，本次失败（回归） |
| 已修复 | 基线失败，本次通过 |
| 仍失败·换层 | 两次都失败，但归因层变了（修了一半，或改出了新问题） |
| 仍失败 | 两次都失败，同一层 |
| 仍通过 | — |
| 新增 / 移除用例 | 只在一侧出现，单列，不进门禁结论 |

### 放行条件

- 新增失败条数 ≤ `--max-regressions`（默认 0）
- 共同用例的 p90 耗时涨幅 ≤ `--latency-tolerance`（默认 20%）

**McNemar 精确检验**只看判定翻转的用例，检验「修好的」和「改坏的」是否对称。
p < 0.05 才能说这次改动确实让通过率变了，而不是偶然。它只作参考，不参与放行判断：
哪怕只有 1 条回归也该拦，这和显著性无关。

### 验证

| 场景 | 结果 | 退出码 |
|---|---|---|
| 同一次运行和自己比 | 仍通过 108 · 仍失败 10，放行 | 0 |
| 改写集：规则轨 → 双轨 | 新增失败 15，McNemar p = 0.0001，拦截 | 1 |
| 反向：双轨 → 规则轨 | 已修复 15，放行 | 0 |
| 同上，`--max-regressions 20` | 放行 | 0 |
| 构造：全部耗时 ×1.3 | p90 上涨 30%，拦截 | — |
| 构造：新增 1 条、移除 1 条 | 单列，不影响结论 | — |
| 构造：一侧 skip | 该条不参与对比 | — |

McNemar 手算核对：(10, 2) → p = 2 × (1 + 12 + 66) / 4096 = 0.0386，与实现一致。

### 还没做的

拿真实修复做一次前后对比，比如修掉 D-001（加权平均）或 D-007（通知扇出）后重新录制，用门禁看「已修复 / 新增失败」。
这需要改软帮手 agent 的 prompt 或工具，属于改被测对象，要等 rein 拍板。
